## Reproductions and fixes

SuperCollider's installation directory contains DXC 1.5. With that working
directory, automatic DXC discovery loaded the old compiler and GPU initialization
failed with "Parent device is lost". The locked wgpu 30 requires DXC 1.8.2502 or
newer. Explicit FXC selection makes the supported shader subset independent of
that DLL. Startup failures also reach the Windows Post pane through stdout.
See the [wgpu compiler contract](https://docs.rs/wgpu/30.0.0/wgpu/enum.Dx12Compiler.html).

Repeated hello packets during GPU initialization generated repeated ready replies.
The SC controller replayed window settings for each reply, causing repeated
surface reconfiguration and startup scheduling stalls. Only the first ready
reply now completes a pending boot. Unit coverage checks duplicates, stopped
controllers and quit state; the formerly failing bus startup check passes.

Windows validation children start suspended, enter a kill-on-close Job Object,
and then resume. Native tests verify descendant cleanup with both a live and an
already-exited parent. See [Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

The typed example smoke initially checked a two-second glide at a fixed time
after process launch, counting variable GPU startup against the glide. It now
polls for the actual endpoint within the unchanged eight-second deadline, retains
the same numeric tolerance and rejects renderer errors. Initial failure retained.

## Limits and next step

Both native interaction runs report one active display, 125% scale, and
1920x1080 framebuffer in fullscreen (1536x864 logical). These are actual window
metrics, not a mixed-DPI monitor-move result. Initial `interactions-nvidia-01/`
failed because the test found several visible helper HWNDs belonging to the
renderer process; the harness now selects the live owned PID plus exact test
title. It never modifies another process's window. The final runs additionally
require fresh frame progress after restore, not merely pre-minimize progress.

The user selected Linux after the Windows interaction step. Source/tool/docs
handoff work does not change the installed 0.0.17 production binary. Physical
input and audio/visual checks are listed in
[the interaction checklist](../WINDOWS_INTERACTION_CHECKS.md); the receiving
Linux workflow is in [LINUX_HANDOFF.md](../LINUX_HANDOFF.md).

The first `sc-zip-17/` invocation omitted the lifecycle test's required renderer
override and requested a nonexistent check name. The corrected invocation in
`sc-zip-17-recheck/` passes against the same extracted package. This was a harness
invocation error, not another renderer boot failure; both logs are preserved.

Each traffic run offered 9,984 updates, received ten pongs and ten status samples,
and progressed from frame 4 to 544. No unexpected renderer error, queue drop or
diagnostic suppression was observed. Peak working sets were 215,764 KiB (NVIDIA)
and 339,940 KiB (Intel). These ten-second modes do not reach the 30-second memory
baseline or scheduled resize action; they establish neither warmed-up memory
stability nor feedback-resize coverage. Separate SC window checks exercise resize.

The initial continuous flood in `runtime-17/run.json` failed live-reply checks,
despite continued frame progress. Traces in `flood-probe-17.log` and
`flood-probe-02.log` show missing probe replies rather than a backlog arriving
after the flood. Windows timer granularity groups offered traffic into bursts;
putting probes before each catch-up burst gives ten live pongs/statuses and a
maximum 0.219-second frame-health gap in both rechecks. The inference is UDP
admission loss for trailing probes, not a demonstrated renderer hang. No renderer
code or load/health assertion was changed for this test correction. The two
passing floods offer 508,032 and 507,776 updates; neither saturates the internal
incoming queue. Internal drop counters do not measure OS-level UDP loss.

Package notice audit: 123 crates, zero missing license texts; human review remains
required. This is not notice/signing clearance. Static imports of the production executable include Windows system libraries,
`VCRUNTIME140.dll` and Universal CRT API sets; no static DXC dependency. A clean
runtime machine without development tools remains untested.

The normal user installation and its automated checks pass. The user should
recompile the open IDE's class library before rerunning examples; compiling a

Installation was performed by the user because this session cannot write outside
